Project view — mockup v2 · the portrait

A picture of what the project is — not what it's doing. No decisions, no in-motion work, no lint, no status. Each band maps to exactly one anchor doc (marked top-right), so the view never becomes a place knowledge secretly lives. Content is repo-pulse's real material, reshaped into the proposed doc set.

Read the whole thing in under a minute and you know the project. That's the only test that matters here. Everything a benchmark put in a project doc that failed this test — file trees, component inventories, session history — is gone.

project-prd
Milestone 1 — specific
▸One command against one repo produces a digest that answers "what happened here?" in under a minute — instead of reading git log
▸Daily and weekly cadence both covered by a single artifact
Direction — beyond milestone 1
▸One combined pulse across several repos at once
Deliberately not
✕Remote/CI integration — GitHub API, PRs, checks. Milestone 1 is purely local git.
✕A persisted database — stored HTML snapshots on disk are enough
✕Watch/daemon/scheduling — run on demand; recurring runs are the user's cron

Near-term must be specific; long-term is allowed to be directional. That split (company-context requires a concrete 12-month target and an explicitly directional 36-month one) dissolves the vision-vs-concreteness fight instead of losing it. How it's built

architecture · absorbs spec

Stack

Python 3 · stdlib only, zero runtime deps git CLI via subprocess, machine-stable formats Single HTML file · inline CSS, no JS/CDN ~/.repo-pulse/ central storage

Shape

git CLI → access layer → commits · branches · churn transforms → renderer → ~/.repo-pulse/<repo>/ latest.html + history/YYYY-MM-DD.html

Invariants

▪The analyzed repo is never written to — read-only git commands only, no exceptions
▪Generated HTML must render fully offline — no external fonts, JS, or CDN
▪All output lives under ~/.repo-pulse/, never inside the target repo
▪Transforms are pure functions over raw git output — the access layer is the only thing that shells out

What's deliberately not here

✕No git library (GitPython/pygit2) — porcelain formats cover every datum we need; a dependency buys nothing
✕No CSS framework — breaks offline rendering, and hairline borders + whitespace need no framework
✕No remote-branch analysis — adds fetch and network concerns to a tool that should work on a plane

No file tree. No component list. Those are stale duplicates of code by construction — hermes hand-maintains both with zero update contract; alirezarezvani's own hub doc says "246 skills" in one section and "355" in another. What's here is only what code can't say: invariants, boundaries, rationale, and the refusals.

This band is why spec.md should dissolve. Stack · approach · constraints are current-state architecture. Keeping both files guarantees the duplication repo-pulse already has — D-001/2/3 each stated twice, once as a Stack bullet and once as a decision record, so changing one means remembering to edit the other.
